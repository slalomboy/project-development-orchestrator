# Failure Patterns

| Symptom | Root layer to inspect first | Prevention asset |
|---|---|---|
| Many screens repeatedly redesigned | workflow, IA, visual target absent | UI gate + state matrix + selected target |
| Frontend optional, backend required | contract drift | one Current schema + contract tests |
| AI output rejected by old validator | AI/output/validator drift | shared structured contract + failing regression |
| System tasks appear in staff files | responsibility drift | four-owner responsibility review |
| Fixed role files do not fit customers | internal modules exposed directly | dynamic person projection |
| Green status but output is stale | readiness based on “saved once” | content signature/freshness gate |
| High test count, unusable DOCX/UI | structural-only verification | semantic, visual and stranger-executor checks |
| New source but old app opens | truth surfaces conflated | source/candidate/installed matrix |
| ZIP/checksum called a release | package truth mistaken for release truth | release surface gate |
| Real data touched during test | runtime isolation failure | explicit test dirs + migration authorization |
| User told to check credentials for format bug | late/generic error classification | earliest structured validation + stable codes |
| Recovery docs disagree | too many current authorities | single Current entry + live reconciliation |
| Long tasks overlap or whole app becomes disabled | concurrency and operation classification absent | conflict key, owner ID, release paths, partial retry, read-only allowlist |

Every repeated failure must become at least one test, gate, stable error code, checklist, template, script, or durable rule. Do not store a narrative without a future behavior change.
